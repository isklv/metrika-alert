# Развёртывание metrika-alert

Сервис опрашивает счётчики Яндекс.Метрики, проверяет события по настроенным
триггерам и доставляет алерты и периодические отчёты в **Telegram**, **ВК Тимс**
и на **webhook**.

Один процесс, одна SQLite-база, только исходящие соединения — сервис работает за
NAT и не требует публичного адреса.

---

## 1. Что понадобится заранее

| Что | Где взять |
|---|---|
| Токен Telegram-бота | [@BotFather](https://t.me/BotFather) → `/newbot` |
| Свой Telegram user ID | [@userinfobot](https://t.me/userinfobot), либо команда `/whoami` уже запущенному боту |
| Токен бота ВК Тимс | бот **@Metabot** в ВК Тимс → `/newbot` (см. §2) |
| Свой ID в ВК Тимс | команда `/whoami` боту после запуска |
| OAuth-токен Метрики | [oauth.yandex.ru](https://oauth.yandex.ru/) → приложение с правом `metrika:read` |
| Номер счётчика | Метрика → Настройки → номер счётчика (8 цифр) |

Нужен минимум один канал доставки. Telegram и ВК Тимс включаются независимо:
пустой токен просто отключает канал.

---

## 2. Бот в ВК Тимс

1. В ВК Тимс найдите бота **@Metabot** и отправьте `/newbot`.
2. Укажите имя бота (например `metrika-alert`). Metabot вернёт токен вида
   `001.0123456789.0123456789:700000001` — это значение `vkteams.bot_token`.
3. Напишите своему боту любое сообщение и отправьте `/whoami` — он ответит вашим
   ID. Добавьте этот ID в `vkteams.admin_ids`.
4. Чтобы алерты шли в групповой чат — добавьте бота в чат, отправьте там
   `/whoami` и используйте показанный `Чат:` как адрес destination.

**Облако или on-premise.** По умолчанию используется облачный контур
`https://myteam.mail.ru/bot/v1`. Для корпоративной установки задайте свой адрес:

```yaml
vkteams:
  base_url: https://myteam.corp.example/bot/v1
```

или переменной `METRIKA_VKTEAMS_BASE`. Сервис проверяет токен при старте и
падает с понятной ошибкой, если контур недоступен — неверный адрес вы увидите
сразу, а не в момент первого алерта.

## 3. Вариант A — Docker Compose (рекомендуется)

```bash
git clone https://github.com/isklv/metrika-alert.git
cd metrika-alert

cat > .env <<'EOF'
METRIKA_BOT_TOKEN=7304642400:AAH...
METRIKA_ADMIN_IDS=123456789
METRIKA_VKTEAMS_TOKEN=001.0123456789.0123456789:700000001
METRIKA_VKTEAMS_ADMINS=admin@corp.example
TZ=Europe/Moscow
EOF
chmod 600 .env

docker compose up -d --build
docker compose logs -f
```

В логе при успешном старте:

```
config loaded from /etc/metrika-alert/config.yaml
db ready at /data/metrika.db
telegram bot ready: @metrika_alert_bot
vkteams bot ready: metrika-alert (700000001) at https://myteam.mail.ru/bot/v1
alert channels: telegram, vkteams
metrika-alert running — press Ctrl+C to stop
```

База лежит в именованном томе `metrika-data` и переживает пересоздание
контейнера. Обновление:

```bash
git pull && docker compose up -d --build
```

### Без Compose

```bash
docker build -t metrika-alert .
docker run -d --name metrika-alert --restart unless-stopped \
  -v metrika-data:/data \
  -e METRIKA_BOT_TOKEN=... \
  -e METRIKA_ADMIN_IDS=123456789 \
  -e METRIKA_VKTEAMS_TOKEN=... \
  -e METRIKA_VKTEAMS_ADMINS=admin@corp.example \
  metrika-alert
```

Чтобы подменить встроенный config.yaml целиком:

```bash
-v $(pwd)/config.yaml:/etc/metrika-alert/config.yaml:ro
```

## 4. Вариант B — systemd

```bash
# 1. Собрать статический бинарь (Go 1.25+)
CGO_ENABLED=0 go build -mod=vendor -ldflags="-s -w" -o metrika-alert ./cmd/server
sudo install -m 755 metrika-alert /usr/local/bin/

# 2. Системный пользователь без shell и домашнего каталога
sudo useradd --system --no-create-home --shell /usr/sbin/nologin metrika

# 3. Конфиг и секреты
sudo mkdir -p /etc/metrika-alert
sudo install -m 644 config.example.yaml /etc/metrika-alert/config.yaml
sudo install -m 600 -o root -g root deploy/env.example /etc/metrika-alert/env
sudo nano /etc/metrika-alert/env     # вписать токены

# 4. Служба
sudo install -m 644 deploy/metrika-alert.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now metrika-alert
sudo journalctl -u metrika-alert -f
```

Токены держите в `/etc/metrika-alert/env` (режим `600`), а не в `config.yaml` —
переменные окружения имеют приоритет над файлом. Юнит уже ограничен
(`ProtectSystem=strict`, `NoNewPrivileges`, сетевые семейства только IPv4/IPv6),
база создаётся systemd в `/var/lib/metrika-alert`.

## 5. Первичная настройка через бота

Напишите боту в Telegram или ВК Тимс — команды одинаковые в обоих.

```
/addcounter
→ Магазин 12345678 y0_AgAAAAA... 15
   имя, номер счётчика, OAuth-токен, интервал проверки в минутах

/addtrigger 1
→ Визиты упали | visits | drop | 40
   имя | метрика | направление | порог%

/addaction
→ vkteams team-chat@corp.example
   куда доставлять: telegram <chat_id> | vkteams <chat_id> | webhook <url>
```

Формат правила разделён вертикальной чертой намеренно: имя может содержать
пробелы, а `goal:42` нельзя резать ни по чему другому.

| Метрика | Что считает |
|---|---|
| `visits` | визиты |
| `users` | уникальные посетители |
| `pageviews` | просмотры страниц |
| `goals` | все достижения целей |
| `goal:<id>` | достижения конкретной цели |

Узнать ID целей: команда `/goals <counter_id>` или `GET /api/goals?counter_id=N`.
Она же показывает готовую строку правила, которую остаётся поправить под себя.

Список целей читается из настроек счётчика, поэтому требует OAuth-токена с
доступом к управлению. Если его нет, команда честно об этом скажет, а алерты по
`goals` и по конкретной цели продолжат работать — ID можно взять в интерфейсе
Метрики.

Направление: `drop` — падение, `rise` — рост, `both` — любое отклонение.

Полная форма правила добавляет необязательные поля:

```
имя | метрика | направление | порог% [мин_база] [недель] [url=...]

Заказы просели | goal:42 | drop | 50 | 5 | 4
Чекаут просел  | visits  | drop | 40 | url=/checkout
Каталог        | visits  | drop | 35 | url~^/catalog/\d+
```

`мин_база` (по умолчанию 10) — порог значимости: если в это время обычно бывает
2 визита, минус один визит формально «падение на 50%», но смысла в таком алерте
нет. `недель` (по умолчанию 4) — глубина истории для базы сравнения.

`url=` ограничивает правило страницами — см. §6.

> Новый счётчик подхватывается на лету — сервис сверяется со списком счётчиков
> раз в полминуты, так что перезапуск не нужен. Удалённый счётчик так же сам
> перестаёт опрашиваться, а изменённый интервал применяется без рестарта.
>
> Проверить, что токен и номер счётчика верны, можно сразу командой `/report`:
> она отвечает за секунды.
>
> ⚠️ Первые алерты появятся не раньше, чем накопится история: правилу нужно
> минимум две прошлые точки того же часа и дня недели, то есть около двух
> недель наблюдений. До этого правило молчит — это защита от алертов,
> построенных на догадках.

Полный список команд — `/help`.

### Если Telegram недоступен

`api.telegram.org` во многих сетях не резолвится или блокируется. Задайте
`METRIKA_PROXY_URL` (схемы `http`, `https`, `socks5` — `socks5h` Go не
поддерживает). В Docker Compose переменная **обязательно** должна быть в секции
`environment:`, иначе `.env` до контейнера не доедет.

Проверить, что прокси применился, можно по строке в логе старта:

```
telegram: через прокси socks5://user:xxxxx@proxy.example.com:1080
```

Если там `telegram: прямое подключение, прокси не задан` — значение не дошло.

Канал, который не поднялся, отключается с предупреждением, а сервис продолжает
работать на остальных: недоступный Telegram не должен заглушать ВК Тимс.

### Куда идут алерты

Пока ни один destination не создан, алерты уходят администраторам из
`admin_ids`. **Как только появился первый destination, рассылка админам
прекращается** — если нужно продолжать получать алерты лично, добавьте себя
через `/addaction` явно.

## 6. Как работают алерты

Сервис использует только **Reporting API** Метрики (`GET /stat/v1/data` и
`/stat/v1/data/bytime`). Он агрегированный, отвечает одним запросом и отдаёт
текущий день — в отличие от Logs API, который данные за сегодня не выдаёт
вообще и для алертов непригоден.

### Скользящее окно с шагом 10 минут

Каждые 10 минут сервис берёт последний **час** трафика и сравнивает его с тем
же промежутком того же дня недели за прошлые недели:

```
вторник 14:20–15:20  ←→  те же 14:20–15:20 прошлых вторников (по умолчанию 4 недели)
```

Ожидаемое значение — **медиана** этих точек, а не среднее. Один праздник,
авария или всплеск от рассылки в истории сдвинул бы среднее настолько, что
реальное падение прошло бы незамеченным.

Почему окно часовое, а шаг десятиминутный:

* **Плоский порог не работает.** У трафика сильный суточный и недельный ритм.
  «Меньше 50 визитов в час» ночью норма, днём инцидент. Поэтому сравнение
  всегда идёт с самим собой в прошлом.
* **Голая десятиминутка слишком шумная.** В ней шестая часть часового трафика,
  и разброс от недели к неделе такой, что порог в процентах теряет смысл.
  Час даёт устойчивую цифру.
* **Шаг даёт скорость.** Падение замечается в пределах примерно получаса
  (шаг + пауза на досчёт), а не в конце часа.

Сужать `window_minutes` до `step_minutes` не нужно — это вернёт шум, ради
устранения которого окно и сделано широким.

### Когда данные считаются готовыми

Измерение всегда отстаёт от текущего момента на `settle_minutes`
(по умолчанию 20): Метрика продолжает досчитывать сессии некоторое время после
того, как они произошли, и замер вплотную к «сейчас» читался бы заниженным.

После простоя сервис догоняет пропущенные окна, но не более
`max_catch_up_steps` за одну проверку, чтобы не выдать пачку устаревших алертов
разом.

### Что настраивается

| Ключ | Смысл | По умолчанию |
|---|---|---|
| `metrika.settle_minutes` | пауза на досчёт данных | `20` |
| `metrika.window_minutes` | ширина окна измерения | `60` |
| `metrika.step_minutes` | шаг окна и периодичность проверки | `10` |
| `metrika.max_catch_up_steps` | сколько пропущенных окон догонять за раз | `6` |

### Ограничение по URL

Правило можно сузить до страниц: `url=/checkout` (URL содержит подстроку) или
`url~^/catalog/\d+` (регулярное выражение). В REST API это поля `url_filter` и
`url_match` (`contains` либо `regexp`).

Под капотом это фильтр Reporting API:

```
filters=EXISTS(ym:pv:URL=@'/checkout')
```

`EXISTS` здесь принципиален. Фильтр по `ym:s:startURL` поймал бы только сессии,
которые **начались** на странице; для чекаута это единицы, тогда как доходят до
него многие. `EXISTS` оставляет каждую сессию, где была хотя бы одна такая
страница.

> ⚠️ Метрика при этом считается **по сессии целиком**. «Визиты с заходом на
> /checkout» — ровно то, что обычно нужно. А `pageviews` с таким фильтром
> посчитает все просмотры этих сессий, а не только просмотры `/checkout`.

Значения экранируются автоматически, регулярное выражение проверяется при
создании правила — ошибку вы увидите сразу, а не через час в логе.

### Стоимость запросов

Правила одного счётчика группируются по области: **один запрос на область за
шаг**. Метрики внутри области объединяются (лимит API — 20 метрик на запрос), а
глубина истории берётся по самому требовательному правилу. Десять правил на
визиты по всему счётчику — это один запрос, а не десять.

Фильтр применяется ко всему запросу, поэтому правила с разными `url=` в один
запрос не соберутся. Три области — три запроса за шаг.

При шаге в 10 минут это **144 запроса в сутки на счётчик**. Если квота API
поджимает или счётчиков много, увеличьте `step_minutes` — реакция станет
медленнее, но точность сравнения не изменится.

Запрашивается детализация `dekaminute`. Если Метрика вернёт данные более
крупными интервалами (такое возможно на очень длинных диапазонах), сервис
сообщит об этом и не станет считать: окно, собранное из корзин неверной ширины,
дало бы уверенно неправильную цифру. Лечится уменьшением `baseline_weeks`
в правиле.

## 7. REST API (опционально)

Выключен по умолчанию. Включение:

```yaml
api:
  enabled: true
  listen_addr: "127.0.0.1:8090"
  auth_token: "..."   # openssl rand -hex 32
```

API создаёт счётчики и читает историю алертов, поэтому **без `auth_token`
публиковать порт наружу нельзя** — при пустом токене сервис пишет предупреждение
в лог при старте. В `docker-compose.yml` порт по умолчанию привязан к `127.0.0.1`.

```bash
TOKEN=...
curl -H "Authorization: Bearer $TOKEN" http://127.0.0.1:8090/api/status
curl -H "Authorization: Bearer $TOKEN" http://127.0.0.1:8090/api/counters
curl -H "Authorization: Bearer $TOKEN" -X POST http://127.0.0.1:8090/api/reports?counter_id=1
```

| Метод и путь | Назначение |
|---|---|
| `GET /healthz` | проба живости, без авторизации |
| `GET /api/status` | счётчики и время последнего алерта |
| `GET,POST /api/counters` | список и создание счётчиков (опрос начнётся сам, без рестарта) |
| `GET,POST /api/monitors?counter_id=N` | страницы мониторинга |
| `GET /api/goals?counter_id=N` | цели счётчика: id, name, type |
| `GET,POST /api/triggers?counter_id=N` | триггеры |
| `GET /api/alert-actions` | destinations доставки |
| `GET /api/alerts?counter_id=N&limit=50` | история алертов |
| `GET,POST /api/reports?counter_id=N` | снимки отчётов, запуск отчёта |

OAuth-токены счётчиков никогда не отдаются в ответах API.

## 8. Резервное копирование

Всё состояние — один файл SQLite (плюс WAL-файлы рядом). Копировать нужно
средствами SQLite, а не `cp`, иначе можно получить незавершённую транзакцию:

```bash
# Docker
docker compose exec metrika-alert sh -c 'sqlite3 /data/metrika.db ".backup /data/backup.db"'
docker compose cp metrika-alert:/data/backup.db ./metrika-$(date +%F).db

# systemd
sudo -u metrika sqlite3 /var/lib/metrika-alert/metrika.db \
  ".backup /var/lib/metrika-alert/backup.db"
```

Восстановление — остановить сервис, положить файл на место `metrika.db`
(удалив `-wal` и `-shm`), запустить.

Схема обновляется автоматически при старте: база, созданная версией без
поддержки ВК Тимс, мигрируется на месте с сохранением всех строк и их ID.

## 9. Диагностика

| Симптом | Причина и что делать |
|---|---|
| `WARNING: telegram.admin_ids is empty` | не задан список админов — бот отклоняет все команды. Напишите боту, он ответит вашим ID |
| `⛔ Доступ запрещён` в ответе бота | ваш ID не в `admin_ids`. Бот показывает нужный ID прямо в сообщении |
| `vkteams: verify token against ...: Invalid token` | неверный `vkteams.bot_token` или указан облачный `base_url` для on-premise контура |
| `vkteams ... : HTTP 404` | неверный `base_url` — проверьте, что путь заканчивается на `/bot/v1` |
| `poller started: no counters configured` | счётчиков нет — добавьте через `/addcounter` |
| Счётчик добавлен, но опроса нет | подождите до полуминуты: список счётчиков сверяется раз в 30 секунд. В логе появится `counter …: проверка запущена` |
| `x509: certificate signed by unknown authority` | в образе нет CA-сертификатов. Пересоберите образ текущим Dockerfile |
| `dial tcp 149.154.166.110:443: i/o timeout` | это **Telegram** (диапазон `149.154.160.0/20`), а не ВК Тимс. Прямой dial в Telegram означает, что прокси не применился: при рабочем прокси в ошибке стоял бы его адрес и префикс `proxyconnect`. Проверьте строку `telegram: через прокси …` в логе старта |
| В логе `telegram: прямое подключение, прокси не задан`, хотя `METRIKA_PROXY_URL` задан | переменная не доехала до процесса. В Docker Compose она должна быть перечислена в `environment:` — одного `.env` мало |
| `proxy_url …: нужна схема http://, https:// или socks5://` | значение без схемы (`proxy:1080`) или `socks5h://`. Go поддерживает только `http`, `https`, `socks5` |
| `WARNING: telegram disabled` | канал отключён, сервис работает дальше на остальных. Недоступность одного канала не роняет процесс |
| `database is locked` | база на сетевом томе (NFS/SMB). Перенесите на локальный диск |
| `metrika API 403: Access denied` | OAuth-токен счётчика не даёт доступа. Нужно право `metrika:read`, а для `/goals` и разбивки по целям в отчёте — доступ к настройкам счётчика |
| Алертов нет совсем | нужна история: правилу требуется минимум две прошлые точки того же часа и дня недели, то есть около двух недель наблюдений |
| `база N ниже порога значимости M` в логе | час слишком тихий для осмысленного сравнения. Уменьшите `мин_база` в правиле, если это осознанно |
| Слишком много алертов ночью | поднимите `мин_база`: в тихие часы проценты скачут на единицах визитов |
| Алерты приходят с опозданием ~30 минут | так и задумано: шаг окна плюс пауза `settle_minutes` на досчёт данных |
| `Metrika returned 1h0m0s intervals, expected 10m0s` | API укрупнил детализацию на слишком длинном диапазоне. Уменьшите `baseline_weeks` в правиле |
| Слишком много запросов к API | при шаге 10 минут это 144 запроса в сутки **на каждую область**. Уменьшите число разных `url=` или увеличьте `step_minutes` |
| Правило с `url=` не срабатывает | проверьте подстроку на реальных URL в Метрике: сравнение идёт по полному адресу страницы, включая протокол и домен |
| `метрика … неизвестна` | в правиле опечатка. Доступны visits, users, pageviews, goals, goal:<id> |
| `db migrated: N event-condition trigger(s) removed` | старые правила по отдельным событиям удалены при обновлении — их нельзя выразить в часовых метриках. Создайте новые через `/addtrigger` |
| `alert dropped — no destinations and no admins configured` | не задан ни один получатель: заполните `admin_ids` или добавьте `/addaction` |
| Алерты перестали приходить лично после `/addaction` | так и задумано: появился явный destination. Добавьте себя через `/addaction` |

Логи:

```bash
docker compose logs -f --tail 100        # Docker
journalctl -u metrika-alert -f           # systemd
```
